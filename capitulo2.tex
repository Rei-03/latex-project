\chapter{Diseño de la solución propuesta para la automatización de la rotación de circuitos eléctricos}

\section{Introducción}

El presente capítulo tiene como objetivo describir y fundamentar el diseño de la solución informática propuesta para resolver el problema científico identificado en el capítulo anterior, relacionado con las limitaciones del proceso manual de rotación de circuitos eléctricos ante déficit de generación en el Despacho Provincial de Carga. En correspondencia con los fundamentos teóricos, regulatorios y metodológicos previamente sistematizados, este capítulo expone la concepción arquitectónica, los artefactos de requisitos, las tecnologías seleccionadas y la descripción funcional de la plataforma web desarrollada \cite{pressman2020}.

El diseño de la solución se enmarca en los principios de la Ingeniería de Software orientada a sistemas de misión crítica, donde la arquitectura constituye un elemento determinante para garantizar calidad, mantenibilidad y desempeño \cite{bass2013}. En entornos energéticos regulados, el diseño no puede limitarse a la implementación funcional, sino que debe asegurar coherencia estructural, separación de responsabilidades y cumplimiento de requisitos operativos de alta disponibilidad \cite{gomez2016}. Por tanto, la solución propuesta fue concebida bajo una \textbf{arquitectura de microservicios}, organizada en una API Gateway que actúa como punto de entrada único y cuatro microservicios especializados: \textbf{auth-ms} (gestión de usuarios y autenticación JWT), \textbf{circuitos-ms} (gestión de circuitos eléctricos), \textbf{rotaciones-ms} (algoritmo de rotación) y \textbf{api-gateway} (orquestación HTTP). La comunicación inter-servicio se realiza mediante el broker de mensajes \textbf{NATS}, garantizando desacoplamiento total. El frontend se desarrolló con \textbf{Next.js 16} (App Router) y \textbf{React 19}, mientras que la persistencia combina \textbf{SQL Server 2008} (datos operativos de circuitos y rotaciones), \textbf{PostgreSQL} (usuarios y roles) y \textbf{Redis} (sesiones y blacklist de tokens JWT).

El capítulo se organiza en tres secciones principales: (1) fundamentos tecnológicos para el desarrollo del sistema; (2) descripción de la solución propuesta; y (3) ingeniería de requisitos del sistema.

\section{Fundamentos Tecnológicos para el Desarrollo del Sistema}

La selección de las tecnologías se fundamentó en tres criterios principales: la necesidad de una arquitectura de microservicios para accesibilidad multiusuario y escalabilidad horizontal, la compatibilidad con la infraestructura de datos legacy en el Despacho Provincial de Carga~\citep{villalba2021}, y la adecuación a los requerimientos operativos de alta disponibilidad del Despacho Nacional de Carga (DNC)~\citep{union2023}.

\subsection{Capa de presentación: Next.js 16 y React 19 (App Router)}
Para el desarrollo de la capa de presentación se seleccionó el framework \textbf{Next.js 16} (con App Router) basado en \textbf{React 19}. Esta decisión permitió el desarrollo de una aplicación web moderna que aprovecha el renderizado híbrido (SSR/SSG) y la navegación optimizada por rutas. El uso de \textbf{Tailwind CSS v4} para el estilizado facilitó la creación de componentes visuales responsivos y de alto rendimiento, optimizados para la visualización de grandes volúmenes de datos operativos. El estado global de autenticación se gestiona mediante \textbf{React Context API}, asegurando sincronización entre vistas sin recargar la página. A diferencia de las aplicaciones de escritorio tradicionales, esta tecnología permite el acceso al sistema desde cualquier nodo de la red local sin necesidad de instalaciones locales.

\subsection{Arquitectura de microservicios (NestJS + NATS)}
Para la capa de servicios se adoptó una \textbf{arquitectura de microservicios} basada en \textbf{NestJS}, dividida en cuatro servicios especializados:

\begin{itemize}
    \item \textbf{auth-ms}: gestiona autenticación, autorización y gestión de usuarios. Implementa JWT con refresh tokens, blacklist en Redis para invalidación de sesiones y hashing de contraseñas con bcrypt. Utiliza \textbf{PostgreSQL} (vía TypeORM) como base de datos de usuarios y \textbf{Redis} para caché de sesiones.
    
    \item \textbf{circuitos-ms}: administra el catálogo de circuitos eléctricos y su consumo. Se conexiona directamente a \textbf{SQL Server 2008} (bases SIGERE y PSFV) mediante el driver \texttt{mssql}, ejecutando consultas optimizadas sobre tablas como \texttt{ap\_circuitos}. Expone sus funcionalidades via mensajes \textbf{NATS}.
    
    \item \textbf{rotaciones-ms}: implementa el núcleo algorítmico de rotación. Consume datos de circuitos (via NATS desde circuitos-ms) y de aseguramientos (SQL Server). Aplica los algoritmos de priorización por bloques y genera las propuestas de rotación. También se conecta a SQL Server para persistencia de resultados.
    
    \item \textbf{api-gateway}: actúa como punto de entrada HTTP único (puerto 3001). Recibe peticiones REST desde el frontend, las traduce a mensajes NATS dirigidos a los microservicios correspondientes y devuelve las respuestas en formato JSON. Centraliza CORS, filtros de error globales y la configuración de seguridad.
\end{itemize}

La comunicación entre microservicios se realiza mediante el \textbf{broker de mensajes NATS}, garantizando desacoplamiento total, escalabilidad horizontal y tolerancia a fallos. Cada microservicio corre en su propio proceso y puede escalar independientemente según la carga. Esta arquitectura contrasta con un monolito tradicional, permitiendo despliegues independientes y mayor resiliencia.

\subsection{Persistencia: bases de datos heterogéneas}
La gestión de persistencia de datos se distribuye según el dominio de cada microservicio:

\begin{itemize}
    \item \textbf{SQL Server 2008}: utilizado por \texttt{circuitos-ms} y \texttt{rotaciones-ms} para acceder a las bases de datos operativas \texttt{SIGERE} y \texttt{PSFV}. Se consultan tablas como \texttt{ap\_circuitos}, \texttt{ap\_Aseguramientos} y \texttt{ap\_curvas} mediante procedimientos almacenados y consultas parametrizadas. El sistema aprovecha la infraestructura ya establecida en el Despacho Provincial.
    
    \item \textbf{PostgreSQL}: empleado por \texttt{auth-ms} (via TypeORM) para almacenar usuarios, roles y permisos. Permite validación de esquemas, transacciones y consultas complejas para gestión de identidad.
    
    \item \textbf{Redis}: utilizado por \texttt{auth-ms} y \texttt{api-gateway} como caché de sesiones y para almacenar la \textbf{blacklist de tokens JWT} invalidados (logout). Garantiza alta disponibilidad y baja latencia para operaciones de autenticación.
\end{itemize}

\textbf{Nota sobre SQL Server 2008:} SQL Server 2008 es una versión cuyo soporte extendido finalizó en 2019. Su uso en el proyecto responde a que la infraestructura del Despacho no ha sido migrada por restricciones presupuestarias y organizativas. Esta limitación se asume como un riesgo controlado: la comunicación con la base de datos se realiza únicamente mediante consultas parametrizadas y procedimientos almacenados, sin exponer la base directamente a la red. No obstante, se recomienda en futuras versiones migrar a SQL Server 2019 o PostgreSQL para garantizar seguridad y soporte a largo plazo.

La integración entre los microservicios modernos y las bases de datos heredadas se realizó mediante conectores optimizados que aseguran tiempos de respuesta inferiores a los 3 segundos, cumpliendo con estándares internacionales para sistemas de automatización energética~\citep{ansi2018}.

\subsection{Metodología de desarrollo y arquitectura de monorepo}
Para la metodología de desarrollo se adoptó la Programación Extrema (XP) como marco ágil de trabajo~\citep{beck2000}. Esta elección permitió organizar el desarrollo en iteraciones cortas (una o dos semanas), donde al final de cada iteración se entregaba un incremento funcional validado directamente por los especialistas del Despacho. La retroalimentación continua del cliente facilitó la adaptación del sistema a las necesidades emergentes del flujo de trabajo real.

El código se organiza en un \textbf{monorepo} gestionado por \textbf{Turborepo}, donde coexisten el frontend (Next.js) y los cuatro microservicios NestJS. Esta estructura facilita la compartición de librerías comunes (paquete \texttt{@une/ms-common} con filtros, DTOs y utilidades) y la orquestación de builds y tests. Cada microservicio posee su propio \texttt{package.json} y puede desplegarse de manera independiente.

\section{Descripción de la Solución Propuesta}

La plataforma web automatizada integra y procesa información dispersa en múltiples fuentes~\citep{villalba2021}, generando órdenes optimizadas de rotación de circuitos ante déficit de generación~\citep{gomez2016}. El sistema implementa una \textbf{arquitectura de microservicios} organizada en tres capas lógicas: frontend (Next.js), API Gateway (NestJS) y microservicios especializados (NestJS + NATS).



El sistema organiza los componentes en los siguientes bloques:

\subsection{Capa de Presentación (Frontend: Next.js 16/React 19)}
La interfaz de usuario se desarrolló como una aplicación web moderna utilizando \textbf{Next.js 16} con App Router y \textbf{React 19}. Permite visualizar el déficit en tiempo real mediante componentes reactivos, supervisar propuestas automatizadas en tablas dinámicas y gestionar excepciones operativas (circuitos asegurados). El estado global de autenticación se gestiona mediante \textbf{Context API}, asegurando sincronización de datos entre vistas sin recargar la página. La aplicación consume exclusivamente la API REST expuesta por el \textbf{api-gateway} (puerto 3001) mediante \textbf{Axios} con interceptores que adjuntan automáticamente el token JWT. Las llamadas siguen el patrón de respuesta \texttt{\{success, data, [error], timestamp\}}.

\subsection{API Gateway (Punto de Entrada HTTP)}
El \textbf{api-gateway} es el único punto de entrada HTTP al sistema (puerto 3001). Implementado con NestJS, recibe peticiones REST del frontend y las traduce a mensajes \textbf{NATS} para enviar a los microservicios correspondientes. Centraliza CORS, filtros de error globales y la validación de tokens JWT (mediante guard). Los endpoints principales son:
\begin{itemize}
    \item \texttt{GET /circuitos}: lista circuitos (consulta a circuitos-ms via NATS)
    \item \texttt{GET /circuitos/with-consumption-and-apagones}: circuitos con consumo y apagones
    \item \texttt{POST /rotaciones/generar}: genera propuesta de rotación (envía mensaje NATS a rotaciones-ms)
    \item \texttt{POST /auth/login}, \texttt{/register}, \texttt{/refresh}: gestión de autenticación (envía a auth-ms)
    \item \texttt{GET /rotaciones/aseguramientos}: lista aseguramientos
\end{itemize}

\subsection{Microservicio de Circuitos (circuitos-ms)}
Este servicio gestiona el catálogo de circuitos eléctricos y sus datos de consumo. Se conecta directamente a \textbf{SQL Server 2008} (SIGERE/PSFV) y expone funcionalidades via NATS. Las consultas más relevantes incluyen:
\begin{itemize}
    \item \texttt{circuitos.findAll}: lista paginada con filtros por bloque y apagabilidad
    \item \texttt{circuitos.findWithConsumptionAndApagones}: retorna circuitos con su último consumo y último apagón (optimizado para rotaciones-ms)
    \item \texttt{circuitos.findOne}: detalles de un circuito específico
\end{itemize}
El servicio aplica optimización de consultas con índices y paginación para manejar grandes volúmenes de datos.

\subsection{Microservicio de Rotaciones (rotaciones-ms)}
Coordina la lógica algorítmica de rotación y consume datos de otros microservicios:

\begin{enumerate}
    \item Obtiene circuitos con consumo desde \textbf{circuitos-ms} via NATS
    \item Obtiene aseguramientos activos desde su propia conexión a \textbf{SQL Server 2008}
    \item Enriquece circuitos con estado de protección (asegurados)
    \item Ejecuta el algoritmo de priorización por bloques (\textbf{RotacionAlgoritmo})
    \item Devuelve lista de circuitos a apagar y a encender
\end{enumerate}

El algoritmo sigue la regla: \textbf{Déficit = MW\_Afectados - MW\_Asegurados}. Los circuitos se ordenan por bloque (prioridad) y se seleccionan secuencialmente hasta cubrir el déficit, con opción de encender circuitos previamente apagados (FIFO).

\subsection{Microservicio de Autenticación (auth-ms)}
Gestiona identidad y acceso con las siguientes características:

\begin{itemize}
    \item \textbf{Autenticación}: login/register con validación de credenciales
    \item \textbf{JWT}: emite access token (corta vida) y refresh token (larga vida)
    \item \textbf{Blacklist}: tokens invalidados (logout) se almacenan en Redis
    \item \textbf{Hash de contraseñas}: bcrypt con salt
    \item \textbf{Base de datos}: usuarios en PostgreSQL (TypeORM)
    \item \textbf{Roles}: Admin y Operador (permisos diferenciados)
\end{itemize}

\subsection{Flujo de Operación del Sistema (vía NATS)}
El proceso completo sigue esta secuencia desacoplada:

\begin{enumerate}
    \item El operador introduce parámetros en la interfaz de React (déficit, fecha, etc).
    \item El frontend envía \texttt{POST /rotaciones/generar} al API Gateway.
    \item El API Gateway recibe la petición HTTP y la traduce a un mensaje NATS \texttt{rotaciones.generar}.
    \item El microservicio \textbf{rotaciones-ms} recibe el mensaje NATS y obtiene datos necesarios:
    \begin{itemize}
        \item Envía mensaje NATS \texttt{circuitos.findWithConsumptionAndApagones} a circuitos-ms
        \item Consulta SQL Server para obtener aseguramientos activos
    \end{itemize}
    \item El algoritmo procesa los datos y devuelve el resultado a rotaciones-ms.
    \item rotaciones-ms responde al mensaje NATS, el API Gateway recibe la respuesta.
    \item El API Gateway devuelve JSON al frontend.
    \item La interfaz se actualiza instantáneamente reflejando la propuesta de rotación.
\end{enumerate}

\subsection{Integración y Seguridad}
La solución se integra con la infraestructura existente mediante compatibilidad total con SQL Server 2008, PostgreSQL y Redis. La seguridad implementa:

\begin{itemize}
    \item \textbf{Autenticación JWT}: access tokens firmados con secreto compartido, refresh tokens con expiración extendida
    \item \textbf{Blacklist en Redis}: tokens invalidados por logout se almacenan hasta su expiración
    \item \textbf{CORS}: configurado en API Gateway para el dominio del frontend
    \item \textbf{Validación de entrada}: DTOs con class-validator en todos los endpoints
    \item \textbf{Transacciones SQL}: integridad en operaciones críticas sobre ap\_Aseguramientos y ap\_circuitos
\end{itemize}

Al ser una aplicación web, garantiza interoperabilidad desde cualquier dispositivo con navegador dentro de la red del Despacho.

\subsection{Ventajas de la Arquitectura de Microservicios}
Esta arquitectura ofrece:

\begin{itemize}
    \item \textbf{Escalabilidad independiente}: cada microservicio puede escalar según su carga (circuitos-ms lectura intensiva, rotaciones-ms cálculo intensivo)
    \item \textbf{Desacoplamiento}: NATS elimina dependencias directas entre servicios
    \item \textbf{Mantenibilidad}: cada servicio posee un área de responsabilidad claramente definida
    \item \textbf{Resiliencia}: fallos en un servicio no colapsan el sistema completo
    \item \textbf{Tecnología heterogénea}: cada servicio puede elegir su esquema de base de datos (SQL Server, PostgreSQL, Redis)
\end{itemize}

La solución reduce el tiempo de respuesta de 45 minutos a segundos, elimina errores manuales y aprovecha plenamente los datos legacy.

\section{Conclusiones del capítulo}

\begin{enumerate}
    \item La selección tecnológica basada en Next.js 16 (App Router), microservicios NestJS (api-gateway, circuitos-ms, rotaciones-ms, auth-ms), comunicación via NATS y bases de datos heterogéneas (SQL Server 2008, PostgreSQL, Redis) respondió a los criterios de arquitectura de microservicios para escalabilidad independiente, desacoplamiento total mediante broker de mensajes, compatibilidad con la infraestructura legacy existente y adecuación a los requerimientos de alta disponibilidad del DNC. Se discute explícitamente la obsolescencia de SQL Server 2008 como una limitación asumida, dejando abierta la recomendación de migración futura.
    
    \item La arquitectura de microservicios desacoplada separa claramente la capa de presentación, la puerta de enlace HTTP, los servicios especializados y las bases de datos. El flujo de operación definido (Frontend $\rightarrow$ API Gateway $\rightarrow$ NATS $\rightarrow$ Microservicio $\rightarrow$ Base de datos) reduce drásticamente los tiempos de respuesta (2-3 s) y elimina errores humanos.
    
    \item La ingeniería de requisitos permitió formalizar las funcionalidades organizadas en cinco módulos lógicos: Seguridad/Autenticación, Circuitos, Aseguramientos, Algoritmo de Rotación y Monitoreo/Apagones. Los objetivos de rendimiento (respuesta $<$ 5 min) fueron superados (2-3 s), como se validará en el Capítulo III.
    
    \item La integración de los fundamentos tecnológicos, la descripción de la solución y la ingeniería de requisitos proporciona una base sólida para la implementación y validación de la plataforma, asegurando coherencia con el problema científico.
\end{enumerate}
