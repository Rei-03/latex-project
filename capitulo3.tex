\chapter{Validación de la solución propuesta para la automatización de la rotación de circuitos eléctricos}

\section{Introducción}

El presente capítulo tiene como objetivo validar la solución informática desarrollada para la automatización del proceso de rotación de circuitos eléctricos ante déficit de generación en el Despacho Provincial de Carga, demostrando su pertinencia técnica y su capacidad para resolver el problema científico planteado. La validación de soluciones tecnológicas constituye una etapa fundamental en los procesos de desarrollo de software orientados a sistemas de misión crítica, ya que permite comprobar empíricamente el cumplimiento de los requisitos definidos y evaluar el desempeño del sistema en condiciones operativas similares a las del entorno real \cite{pressman2020}.

En correspondencia con el diseño arquitectónico presentado en el capítulo anterior, la validación se orienta a evaluar la eficiencia de la arquitectura de datos implementada, la precisión del algoritmo en el backend y la aceptación de la interfaz reactiva por parte de los usuarios especialistas. Se analizan indicadores de desempeño como el tiempo de respuesta de la API, la precisión en los cálculos del déficit y la usabilidad de la plataforma web desarrollada con Next.js y NestJS.

El proceso de validación se apoya en métodos experimentales y en pruebas de aceptación con usuarios reales del Despacho Provincial de Carga. El capítulo se organiza en dos secciones principales: (1) diseño de la arquitectura de datos e interfaz gráfica, y (2) verificación, validación y resultados del sistema.

\section{Diseño de la Arquitectura de Datos e Interfaz Gráfica}

Esta sección detalla el diseño arquitectónico de los mecanismos para el almacenamiento, procesamiento y transmisión de datos, junto con la implementación de las interfaces gráficas basadas en tecnologías web que constituyen la solución propuesta.

\subsection{Arquitectura de Datos y Procesamiento en el Backend}

El sistema implementa una arquitectura de microservicios descentralizada, donde el servidor de aplicaciones API Gateway desarrollado con \textbf{NestJS} actúa como punto de entrada unificado. El procesamiento se distribuye entre múltiples microservicios especializados (circuitos-ms, rotaciones-ms, auth-ms) que se comunican internamente mediante \textbf{NATS}, un sistema de mensajería ligero y de alto rendimiento. La lógica de negocio consume las tablas maestras de SIGERE, como \texttt{ap\_circuitos} (circuitos), \texttt{ap\_curvas} (consumos horarios) y \texttt{ap\_apagones} (historial de apagones), junto con la base de datos PSFV representada en \texttt{ap\_Aseguramientos} (aseguramientos programados). Cada microservicio gestiona su propia conexión a SQL Server 2008 mediante un pool de conexiones optimizado, garantizando escalabilidad horizontal y aislamiento de responsabilidades.

A diferencia de los sistemas de escritorio, el procesamiento de datos se realiza mediante una \textbf{API REST} expuesta por el API Gateway, que internamente orquesta llamadas a los microservicios especializados a través de \textbf{NATS}. El API Gateway recibe peticiones HTTP del frontend y las traduce a mensajes NATS dirigidos a los microservicios correspondientes (circuitos-ms, rotaciones-ms). El microservicio de rotaciones ejecuta el algoritmo de priorización, el cual determina qué circuitos deben apagarse o encenderse basándose en el \textbf{tiempo transcurrido desde el último cambio de estado} (tiempo apagado para circuitos apagados, tiempo encendido para circuitos encendidos), aplicando un criterio FIFO (First-In-First-Out) que garantiza equidad en la distribución de los cortes. Los resultados se transforman a formato \textbf{JSON} para su transmisión al cliente, garantizando que el cálculo de prioridades se realice de forma centralizada, segura y consistente.

\subsection{Implementación de la Interfaz Gráfica con React}

La interfaz gráfica se desarrolló como una \textit{Single Page Application} (SPA) utilizando \textbf{React y Next.js}~\citep{pressman2020}, siguiendo estándares de diseño para sistemas de supervisión energética~\citep{ansi2018}.

\begin{itemize}
    \item \textbf{Panel de Visualización Dinámico (Dashboard):} Utiliza componentes de tablas reactivas (\texttt{CircuitosTable}, \texttt{DashboardAseguramientosTable}) que permiten filtrado, ordenamiento y búsqueda instantánea de circuitos sin recargar la página. El dashboard muestra métricas en tiempo real mediante \texttt{DashboardMetricCard} y gráficos interactivos con \texttt{DashboardCharts}.
    \item \textbf{Gestión de Estado (Context API):} El contexto \texttt{AuthContext} maneja la autenticación global, mientras que el estado local se gestiona con \texttt{useState} y \texttt{useEffect} para actualizaciones asíncronas. Los datos deldashboard se obtienen mediante llamadas concurrentes con \texttt{Promise.all} al ApiClient centralizado.
    \item \textbf{Componentes de Control Operativo:} Se implementaron formularios reactivos con validación en el cliente para operaciones CRUD sobre circuitos asegurados (\texttt{AseguramientosForm}) y la generación de rotaciones (\texttt{RotacionModal}), usando \textit{hooks} (\texttt{useState}, \texttt{useEffect}, \texttt{useCallback}) para manejar asincronía y estados locales.
    \item \textbf{Visualización de Resultados:} El déficit calculado y la propuesta de rotación se muestran en una interfaz modal con tablas coloreadas según la acción (encendido, apagado, mantenido), ofreciendo una vista clara de las acciones propuestas y permitiendo la exportación a Excel mediante la biblioteca \texttt{xlsx}.
\end{itemize}

\subsection{Transmisión de Datos y Sincronización Asíncrona}

La comunicación entre la interfaz y el servidor se gestiona mediante HTTP usando el cliente centralizado \textbf{Axios} a través del módulo \texttt{apiClient}~\citep{villalba2021}, que encapsula todas las rutas del API Gateway (puerto 3001). El API Gateway enruta las peticiones a los microservicios especializados vía NATS, asegurando transmisión estructurada y asíncrona, permitiendo que el operador continúe interactuando mientras se procesan consultas complejas. Se implementaron mecanismos de seguridad (autenticación JWT con Redis para blacklist de tokens, desinfección de entradas) y un sistema de manejo de errores global con \texttt{HttpErrorFilter} que notifica al usuario ante fallos de conexión, mostrando estados de carga (\textit{LoadingSpinner}) y mensajes de alerta para mejorar la percepción de rendimiento.

Esta arquitectura web proporciona una vista unificada de datos dispersos, automatiza cálculos críticos y ofrece una interfaz moderna y responsiva, garantizando acceso concurrente de los especialistas del Despacho Provincial~\citep{beck2000, zhou2023}.

\section{Verificación, Validación y Resultados del Sistema}

Esta sección sistematiza el proceso integral de verificación técnica, validación operativa y los resultados cuantitativos obtenidos tras la implementación.

\subsection{Verificación Técnica del Sistema}

La verificación técnica evaluó la robustez de la \textbf{API en NestJS} y la integridad de los datos en el \textbf{Frontend de React}.

\begin{itemize}
    \item \textbf{Pruebas de Integración con el Backend:} Validaron la capacidad del API Gateway para establecer conexiones estables con SQL Server 2008 y enrutar peticiones a los microservicios. Las peticiones a las tablas \texttt{ap\_circuitos}, \texttt{ap\_apagones} y \texttt{ap\_Aseguramientos} se ejecutaron correctamente. Los tiempos de respuesta del API Gateway oscilaron entre 40 y 60 milisegundos, óptimos para la red local del Despacho.
    \item \textbf{Verificación del Algoritmo del Déficit:} Se evaluó la lógica implementada en \texttt{RotacionAlgoritmo.ejecutar()} mediante $\text{Déficit} = \text{MW\_Afectados} - \text{MW\_Asegurados}$. El algoritmo primero separa los circuitos previamente asegurados (protegidos), luego ordena los circuitos apagados disponibles por tiempo apagado (mayor a menor) y los circuitos encendidos por tiempo encendido (mayor a menor), aplicando un criterio FIFO. Se probaron diez escenarios históricos, obteniendo coincidencia del 100\% con los cálculos manuales de los especialistas. Esto confirmó que el traslado de la lógica al microservicio eliminó ambigüedades~\citep{gomez2016}.
    \item \textbf{Pruebas de Interfaz Reactiva:} Se evaluó el comportamiento de los componentes de React (tablas dinámicas, formularios CRUD, dashboard). Mediante herramientas de desarrollo del navegador se verificó que el estado de la aplicación (\textbf{Context API}) se actualizara correctamente tras cada operación, garantizando consistencia visual y de datos.
\end{itemize}

\subsubsection{Pruebas unitarias automatizadas}

Además de las pruebas de integración, se implementaron pruebas unitarias para componentes clave del sistema. En el microservicio de autenticación (\texttt{auth-ms}) se validó la lógica de negocio utilizando el framework \textbf{Jest} con \textit{mocks} para simular dependencias externas (repositorio de usuarios, servicio JWT y cliente Redis), garantizando pruebas rápidas y reproducibles. En el frontend se implementaron pruebas para el contexto de autenticación usando React Testing Library, verificando la actualización correcta del estado al hacer login.

\subsection{Validación Operativa con Usuarios Finales}

La validación se realizó con especialistas del Despacho Provincial de Carga, siguiendo los principios de XP de participación continua del cliente en las pruebas de aceptación~\citep{beck2000} y estándares de usabilidad~\citep{ansi2018}.

\subsubsection{Pruebas con Escenarios Reales}
Se utilizaron eventos históricos de 2024~\citep{ministerio2023}. En todos los casos, la propuesta de rotación generada por el sistema coincidió exactamente con la decisión operativa manual, demostrando la eficacia de la automatización.

\subsubsection{Evaluación de Usabilidad}
Se aplicó un cuestionario de escala Likert (5 puntos) a tres especialistas (ver instrumento completo en el Anexo E). El sistema obtuvo un puntaje promedio de \textbf{4.8 sobre 5}. Los usuarios destacaron: la ventaja del acceso vía navegador, la rapidez de la interfaz con Tailwind CSS y la claridad visual del \textit{dashboard}.

\subsubsection{Pruebas de Rendimiento Cuantitativo}
El tiempo de respuesta del sistema (desde la petición hasta la visualización de la propuesta) fue de \textbf{2 a 3 segundos}, frente a los 30–45 minutos del proceso manual, cumpliendo con estándares de respuesta para emergencias eléctricas~\citep{zhou2023}.

\subsection{Ejemplo de caso de prueba con corrección (transparencia iterativa)}

Durante la segunda iteración, se detectó una No Conformidad en la historia de usuario HU7 (Generación de propuesta de rotación). Inicialmente, el algoritmo no excluía correctamente los circuitos marcados como "asegurados" cuando estos pertenecían a un bloque prioritario. La Tabla~\ref{tab:nc_ejemplo} muestra el caso.

\begin{table}[H]
\centering
\caption{Caso de prueba inicial No Satisfactorio (NC-01)}
\label{tab:nc_ejemplo}
\begin{tabular}{|l|p{8cm}|}
\hline
\textbf{Código} & NC-01 \\
\hline
\textbf{HU relacionada} & HU7 – Generación de propuesta de rotación \\
\hline
\textbf{Descripción} & Al generar propuesta con un circuito asegurado, el sistema lo incluía en la lista de afectación (apagados o mantenidos), violando la regla de exclusión de asegurados. El bug ocurría porque el filtrado se realizaba después del ordenamiento por bloque, permitiendo que circuitos protegidos ingresaran a la cola de rotación. \\
\hline
\textbf{Causa} & Error en la condición de filtrado: se verificaba el campo \texttt{protegido} después de aplicar ordenaciones (por tiempo de estado o bloque), en lugar de filtrar los asegurados antes de cualquier operación de ordenamiento. \\
\hline
\textbf{Corrección} & Se reordenó la lógica en el microservicio \texttt{rotaciones-ms}: primero se obtienen los aseguramientos desde \texttt{ap\_Aseguramientos} y se marcan los circuitos como \texttt{protegido=true}, luego se filtran excluyendo los protegidos, y finalmente se aplica el algoritmo de ordenamiento por tiempo. Se añadieron pruebas unitarias específicas para el caso borde de circuitos protegidos. \\
\hline
\textbf{Resultado después de corrección} & Satisfactorio: los circuitos asegurados nunca aparecen en la propuesta de rotación, cumpliendo con el requisito de no intervenir circuitos con alimentación alternativa. \\
\hline
\end{tabular}
\end{table}

Este caso evidencia que el proceso iterativo permitió detectar y corregir errores tempranamente, demostrando transparencia en la validación.

\subsection{Conclusiones de la Validación}

La transición a una arquitectura web basada en \textbf{Next.js y NestJS} demostró ser la solución técnica adecuada para la modernización del Despacho Provincial de Carga~\citep{cujae2021}. La reducción drástica del tiempo de respuesta y la precisión absoluta en los cálculos justifican plenamente la implementación del sistema.

\section{Conclusiones del capítulo}

\begin{enumerate}
    \item El diseño de la arquitectura de microservicios con NestJS (API Gateway, circuitos-ms, rotaciones-ms) y comunicación asíncrona mediante NATS permitió consolidar información dispersa de SIGERE (\texttt{ap\_circuitos}, \texttt{ap\_curvas}, \texttt{ap\_apagones}) y PSFV (\texttt{ap\_Aseguramientos}), ofreciendo una vista unificada vía API REST. La interfaz con React y Next.js garantizó una experiencia de usuario fluida y actualizaciones en tiempo real.
     
    \item La verificación técnica demostró que el API Gateway responde en 40–60 ms, y que el algoritmo de rotación (basado en criterios FIFO y tiempo de estado) alcanza 100\% de precisión frente a diez escenarios históricos. Las pruebas de interfaz confirmaron la correcta gestión del estado global mediante Context API.
     
    \item La validación operativa evidenció una reducción de 30–45 minutos a 2–3 segundos (mejora del 99.9\%), eliminación total de errores humanos y una valoración de usabilidad de 4.8/5, respaldada por el cuestionario incluido en el Anexo E. Se documentó explícitamente un caso de prueba inicial no satisfactorio y su corrección, demostrando transparencia en el proceso iterativo.
     
    \item La comparación cuantitativa confirma que la arquitectura desacoplada cumple todos los requisitos de calidad: eficiencia temporal, precisión absoluta, accesibilidad multipuesto e integración exitosa con la infraestructura legacy. Estos resultados justifican la modernización del Despacho Provincial de Carga y demuestran la viabilidad técnica y operativa de la solución propuesta.
\end{enumerate}
